## 判断

产品有比较完整的基础：订单账本、租约隔离、签名前检查、风控、对账、审计、测试和部署流程都已具备。但目前存在多处跨模块契约不一致，尤其是“界面显示的状态”“保存的配置”“Worker 实际行为”之间不一致。现阶段应优先把真实资金路径与操作闭环修好，再扩充策略、图表或模型。

不能因为单元测试通过，就认定已经适合无人值守实盘。也不沿用旧报告的“大厂水准”或 9 分以上评分：这些结论没有替代关键流程验证的作用。本次未发现能确认的 JWT 伪造、owner 越权或跨账户读取漏洞，但确实发现限流绕过、风控金额低估及订单状态错误。

## 需要优先修复的问题

### F01 · P1 · 风控使用预期成本，真实限价订单可突破上限

**位置：** `backend/src/polybot/strategy.py:238`、`backend/src/polybot/brokers/polymarket.py:271`。

策略用扫描盘口计算的预期成交成本作为 `notional_usd`。风控和 broker 检查这一数字，最终签署的订单却允许全部 `size` 以 `limit_price` 成交，两者不等价。

**离线复现：** 单笔上限 $5；卖盘前 40 股价格 $0.10，后续价格 $0.50。程序生成 42 股、限价 $0.50，预期成本 $5，风控通过并调用提交接口。订单允许的最大本金是 **$21**。若低价流动性在实际成交前消失，实际成交金额可能明显超过设定上限。这不是已经发生 $21 扣款的证明，而是签署授权金额超限的确定性复现。

**修复：** 区分预期成交成本和最大承诺本金；数量、余额、单笔、事件和总敞口限制按限价本金加最坏费用计算，并在签名前独立复核。预期成本只用于收益估计。

**验收：** 多档盘口、低价档撤单、跳价、部分成交和费用变化下，真实签名允许的最大支出始终不超过限制。不能只断言 `candidate.notional_usd <= cap`。

### F02 · P1 · 模式切换查询错误的表，界面可显示 Paper 而 Worker 仍在 Live

**位置：** `backend/src/polybot/personal_execution.py:116`、`backend/src/polybot/worker.py:696`、`backend/src/polybot/api_dependencies.py:87`。

Worker 查询 `runtime_profiles`，但迁移创建的是 `account_runtime_profiles`。读取失败被捕获后继续使用旧模式。API 却直接根据已保存的 `desired_mode` 推导并返回所谓生效模式。

**确认依据：** 全部 SQL 迁移没有创建 `runtime_profiles` 表或视图；保存配置的路径写入 `account_runtime_profiles`。现有模式测试用 fake repository，没有覆盖真实表名。

**影响：** 正常部署后模式热切换失效。若已经开启并运行实盘，用户选择 Paper 后，界面可能显示 Paper，而后台仍按旧实盘模式运行。实际是否继续下单仍受授权、租约及其他风控条件约束，但不能把界面切换视为已停实盘。

**修复：** 更正表名；明确返回目标模式、Worker 已确认的实际模式、生效版本和切换状态。只有完成撤单、模式对齐并由 Worker 确认后，才能显示切换成功。

**验收：** 使用真实 Supabase/Postgres schema 跑 Live→Paper、Paper→Canary；模拟读取失败、撤单失败和重启，验证 UI 不提前宣布切换完成。

### F03 · P1 · 风控档位“已应用”，实际个人 Worker 不使用新限额

**位置：** `apps/web/app/settings/page.tsx:178`、`backend/src/polybot/api.py:944`、`backend/src/polybot/api.py:1144`、`backend/src/polybot/api.py:1221`、`backend/src/polybot/runtime.py:283`。

设置页将风险档位写入数据库，并提示已应用。个人模式的状态和 RiskEngine 却仍使用环境变量，没有读取该风险策略。

另一个入口问题是该接口要求 AAL2，而当前登录仅有密码登录，没有可用的 MFA 绑定与升级会话流程。

**离线复现：** 普通 AAL1 登录应用档位返回 403；合成 AAL2 会话可以保存单笔上限 $2，但 `/v1/status` 仍显示环境变量中的 $17，运行时同样使用旧值。

**修复：** 风控统一配置来源，返回实际生效版本并由 Worker 确认；明确个人模式的授权策略并补完整 MFA 流程。如果决定只允许环境变量修改，应移除无效的“应用”操作并准确说明配置方式，不能仅绕过鉴权。

**验收：** 通过界面调低限额后，用实际运行时验证超出新值的订单被拒绝；版本尚未生效时明确提示待应用。

### F04 · P1 · 下单与停用竞态中，已成交订单被误标为已撤销

**位置：** `backend/src/polybot/brokers/polymarket.py:443`、`backend/src/polybot/stores/supabase_reconcile.py:156`。

单笔订单 POST 期间控制版本发生变化时，代码尝试撤单，然后仅凭“开放订单为零”就保存 `CANCELLED`。完全成交同样会导致开放订单为零。

**离线复现：** POST 返回 `status="matched"`、order ID 和 trade IDs，控制版本在 POST 内改变；撤单后查询无挂单。最终结果为 `cancelled`，记录成交量为 0，未决订单检查返回 False，还提示已撤单。终态取消订单被订单修复扫描排除；后续成交扫描可能补回成交，但本次状态结论与提前解除未决门禁已经不成立。

**修复：** 与批量路径一致保留 `ERROR/unknown`，完成订单与成交对账后才能判断撤销、部分成交或全部成交。保留未决门禁直至核实。

**验收：** 覆盖停用与全部成交、部分成交、响应超时、撤单响应之间的竞态。现有 `tests/test_safety.py:798` 固化了 `CANCELLED + 无未决` 的错误断言，需要修正测试期待。

### F05 · P1 · 历史手动赎回导致对账持续失败，重置基准无法恢复

**位置：** `backend/src/polybot/reconcile.py:298`、`backend/src/polybot/stores/ledger.py:105`。

成交记录有基准和隔离逻辑，但 REDEEM/SPLIT/MERGE/CONVERSION 活动直接进入活动台账。历史手动赎回没有机器人成交成本基础，因此账本重建报错。

**离线复现：** 钱包无当前仓位和挂单，仅有 30 天前 $10 的手动 REDEEM；对账基准设为 5 分钟前仍失败。把基准重置到现在后继续报 `redeem activity has no complete preceding token cost basis`。

**修复：** 活动和成交统一按机器人归属及基准处理。已写入的外部活动需要安全迁移到隔离记录，保留审计轨迹；不能直接忽略全部活动，否则会掩盖真实持仓成本问题。

**验收：** 完整 REST 对账覆盖历史手动赎回、拆分、合并、隔离资产后续赎回，以及机器人自身正常赎回。

### F06 · P1 · 状态未知或过期被展示为“不会提交新实盘订单”

**位置：** `apps/web/app/page.tsx:224`、`apps/web/app/page.tsx:455`。

初次加载失败时没有 control，或者网络中断后旧授权倒计时结束，`effectivelyArmed` 为 False，于是页面显示“已锁定”“不会提交新实盘订单”。缺少最新状态不能证明后台已停用；后台进程可能独立续期并继续运行。

**修复：** 将未知、过期、确认锁定和授权有效分开。显示最后确认时间，过期后去掉安全保证文案。模式与风险配置同样应标明实际确认状态。

**验收：** 实盘运行时模拟 API 超时、断网、授权续期和重新连接；从未获取状态时不出现安全结论。

## 产品流程和长期运行问题

### F07 · P2 · 首次模拟已成功提交，向导却查询错误任务并报失败

**位置：** `apps/web/app/setup/page.tsx:101`、`apps/web/app/setup/page.tsx:129`、`backend/src/polybot/api.py:1118`。

个人周期接口返回个人 request ID。向导只要看到 ID 就把它当成租户 job ID，查询 `/v1/jobs/{id}`。它准备的个人状态轮询分支不会走到。

**离线复现：** POST `/v1/personal/cycles/run` 返回 202；查询对应 `/v1/jobs/{id}` 返回 404。

**修复与验收：** 统一任务状态契约，或复用个人周期状态轮询，并绑定具体请求。已登录的“首次 Paper 运行→等待→结果”必须有集成测试。

### F08 · P2 · 首次出现非空评分后，绩效页会报错

**位置：** `apps/web/app/performance/page.tsx:48`、`apps/web/app/performance/page.tsx:63`、`backend/src/polybot/performance.py:45`。

后端 `Decimal` 经 Pydantic/FastAPI 序列化为字符串；前端 TypeScript 接口将其当 number，并直接调用 `.toFixed()`。类型声明不会转换网络数据。

**离线复现：** 后端实际模型输出 `"brier_score":"0.25"`、`"log_loss":"0.6931"`；前端评分格式化函数无法处理该字符串。

**修复与验收：** 在 API 边界解析并验证有限数值，明确钱和概率的序列化契约；用后端真实 JSON 样例测试有数据、空数据和异常数据三种状态。

次要显示错误：同页 `:162` 在 snapshot 为空时显示绿色 `VALIDATED`，应改为未获取或待验证。

### F09 · P2 · 限流可被未验证的 Bearer 字符串绕过，缓存无硬上限

**位置：** `backend/src/polybot/api_models.py:85`、`backend/src/polybot/api_models.py:94`、`backend/src/polybot/api.py:502`。

认证前任意 `Bearer ...` 都会成为限流身份。改变假 token 即可得到新额度。缓存超过 8192 条后只删除过期项，当前窗口内记录仍全部保留，每个请求还会遍历缓存。

**离线复现：** 同一 IP、9,000 个不同的无效 Bearer 字符串，全部通过限流，缓存留下 9,000 项。未向线上服务发送攻击流量。

公开 `/health` 不要求 JWT，却会进行数据库健康查询，因此存在放大数据库负载的路径。API 与交易 Worker 共进程，还可能争用 CPU、内存和事件循环资源。

**修复与验收：** 认证前按可信客户端 IP 限流，认证后按已验证账户叠加限额；缓存严格限容。健康检查应有独立受控额度或短缓存。以假 token 轮换测试额度和缓存容量，不只测固定 token。

### F10 · P2 · 个人部署未启动预测结算任务，校准缺少数据来源

**位置：** `backend/src/polybot/api.py:202`、`backend/src/polybot/worker.py:768`；对照 `backend/src/polybot/tenant_execution.py:658`。

个人 Worker 会定时读取预测结算结果来更新校准曲线，但 `MarketResolutionWorker` 仅在旧的 tenant queue 路径创建。全源码中没有个人模式调用 `record_market_resolution` 的替代写入路径，SQL 也没有自动填充该表的触发器。

**影响：** 按 README 的单个 personal 服务部署，预测结果不会因市场到期而自动进入 `forecast_outcomes`，绩效与校准可能长期空白。已有历史数据或外部自行运行结算任务的部署除外。

**修复与验收：** 把结算任务纳入 personal lifespan 的启动、停止和健康管理。用一条预测、一个模拟已结算市场验证“预测→结算→评分→校准刷新”的完整链路。

### F11 · P2 · 模拟持仓离开扫描榜单后无法恢复查询

**位置：** `backend/src/polybot/brokers/paper.py:232`、`backend/src/polybot/market.py:145`。

PaperBroker 把 Gamma market ID 存为 CTF condition ID。持仓市场不再处于 top-N 扫描范围后，补查用错 ID，因此无法继续针对该持仓做主动退出决策。

**离线复现：** 市场 ID 为 m1、condition ID 为 c1，真实 PaperBroker.submit 建仓后退出扫描列表；查询请求用 `condition_ids=["m1"]`，恢复数量为 0，并记录 `held_market_lookup_error:LookupError`。

**修复与验收：** 在意图和模拟持仓中保存真实 condition ID，或从持久市场数据解析。测试必须经过真实模拟买入路径，不能手工修正内部字典再测退出。

### F12 · P2 · 仓位明细盈亏字段不匹配

**位置：** `apps/web/app/assets/page.tsx:111`、`backend/src/polybot/jobs/supabase.py:305`。

后端返回 `unrealized_pnl_pusd`，前端只读取 `pnl_usd` / `unrealized_pnl_usd`。因此汇总有数据，单仓盈亏却显示为 `—`。

**修复与验收：** 统一字段与单位，用真实 API 响应校验每笔成本、现值和浮动盈亏，避免靠前端假数据通过测试。

### F13 · P2 · 普通操作忙碌时，紧急停用按钮被禁用

**位置：** `apps/web/app/page.tsx:268`、`apps/web/app/page.tsx:287`、`apps/web/app/page.tsx:593`。

按钮使用共享 `busy !== null` 条件。运行周期请求或恢复实盘期间，即使用户想立即停用也无法点击。正常请求最长等待约 30 秒，随后刷新还可能等待约 15 秒。

**修复与验收：** 停用有独立请求状态并优先执行，仅自身请求防重复；前一次“恢复”操作的迟到结果不能覆盖已发生的停用。用延迟响应测试运行、恢复和停用的交错顺序。

### F14 · P2 · 模拟和实盘权益被画进同一条净值曲线

**位置：** `backend/src/polybot/engine.py:240`、`backend/src/polybot/jobs/supabase.py:983`、`apps/web/components/EquityChart.tsx:37`。

记录时 source 区分 paper/live/canary，但查询只按 account ID，前端又丢弃 source，直接连接成一条线。模拟资金 $1,000 与实盘资金 $20 会被展示成同一账户曲线的骤降，无法据此判断策略回撤。即便当前模式热切换有 F02，用户通过重新部署切换仍会触发历史混合。

**修复与验收：** 按资金账本/运行模式分离净值序列，切换时标明口径；入金、出金与交易收益也应分开。混合数据测试不能产生虚假的策略盈亏。

## 依赖更新

`npm audit --omit=dev` 报告 2 个 moderate 条目，来源是同一 PostCSS 公告及其对 Next.js 的间接影响，不代表发现了两个独立的远程可利用漏洞。

当前 package override 固定 PostCSS 8.5.21。公告已列出 8.5.23 为修复版本，旧验证文档“尚无上游修复”应更新。漏洞需要处理攻击者控制的 CSS、未设置特定源文件选项并暴露生成的 source map；本次没有发现本产品暴露此类 CSS 处理入口，不把它描述成已验证的线上数据泄露。

建议升级到修复版本并重新执行构建/审计，无须因 npm 自动建议而直接盲升 Next.js 大版本。来源：[PostCSS 安全公告 GHSA-fxqj-rqcc-2cmp](https://github.com/advisories/GHSA-fxqj-rqcc-2cmp)。

## 产品优化建议

以下是体验与运营改进方向，与上面的确认缺陷分开验收。

| 优先方向 | 具体改法 | 对用户的价值 |
|---|---|---|
| 首页围绕真实运行状态组织 | 首屏显示实际模式、最近心跳、最近成功周期、下次运行、当前阻塞项、有效风险限额；技术地址和控制版本折叠 | 一眼判断是否正在工作、是否涉及真实资金 |
| 操作必须有完整结果 | 提交后展示扫描→证据→预测→风控→执行→对账；没有成交时给出主要原因和下一步 | 不会把正常观望误认为故障，避免反复点运行 |
| 停用结果可核实 | 展示停用已受理、禁止新单、剩余挂单、撤单确认、是否有未决成交；明确停用不等于平仓 | 用户能确认操作是否真正完成 |
| 完整订单与资产视图 | 利用后端已有 orders/open_orders/recent_fills，展示价格、剩余量、状态、成交费用和撤单进度 | 能对照交易所检查执行结果 |
| 分析解释为什么交易 | 同一卡片展示模型概率、盘口价格、费用、保守区间、成本后优势、风控拒绝原因 | 从“模型说了什么”走向“这次交易为何成立” |
| 研究、模拟、实盘报告分开 | 模式、日期、市场、模型筛选；显示样本数、不同市场数、成交率、滑点和成本后收益 | 避免模拟余额或重复预测使结果看起来更好 |
| AI 成本账本完整化 | 将证据搜索、主模型、复核、fallback、重试、失败后的用量纳入统一统计；未知定价标为未知 | 成本可解释，也能定义真正可执行的调用或金额预算 |
| 故障提示可执行 | 每个原因给明确动作与入口，附最后成功时间；账户增加找回密码和 MFA 流程 | 减少看日志猜原因和登录后无法继续的情况 |
| 独立存活监控与恢复演练 | 在进程外探测可用性和 Worker 新鲜度；实际演练数据库恢复 | 当前进程内 monitor 在进程死亡时也会停止，不能替代外部监控 |

AI 校准还应增加模型/版本/类别区分、原始概率与校准后概率分开保存、独立市场数量与时间外验证。当前账号级预测行数不能直接视为独立样本数，同一市场反复预测会重复贡献同一个结局。

## 建议修复顺序与完成标准

1. **资金及控制正确性：** F01、F02、F03、F04、F06、F13。实际签署金额不超限，界面不虚报安全状态，停用不会被普通动作阻塞，模式与风控有 Worker 确认。
2. **正常启动和恢复：** F05、F07、F09。旧钱包可解释地接入，首次运行得到正确结果，公开 API 限流有效。
3. **数据与研究闭环：** F08、F10、F11、F12、F14。市场结算后能评分，真实数据能渲染，模拟持仓能恢复管理，不混合模拟和实盘口径。
4. **体验与运营：** 订单详情、决策解释、筛选、完整 AI 成本、外部监控和恢复演练。

新增验证应优先覆盖跨层契约，而不是继续堆叠内部函数测试：真实数据库表名、实际 JSON 序列化、已登录关键流程、交易所部分成交与超时响应、重启和断网状态。现有测试全绿与本次发现并不矛盾：多数缺陷位于目前测试替身绕过的边界。

本报告不认定线上已发生资金损失，也不认定修完这些问题就证明策略有效。上述 P1 问题关闭并完成隔离环境验证前，不建议把当前版本作为可无人值守的实盘系统。
